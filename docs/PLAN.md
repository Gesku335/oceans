# OCEAN — план разработки для Claude Code

Биржа фермерских продуктов (B2B) с цифровым меню и «цифровым паспортом» происхождения блюд.
Источник требований: `OCEAN.pdf` (концепт). Всё, чего в концепте нет, помечено как **[допущение]** и должно быть подтверждено владельцем продукта до реализации соответствующего этапа.

---

## 0. Как работать с этим файлом (инструкция для Claude Code)

1. Положи этот файл в корень репозитория как `docs/PLAN.md`, а блок ниже — как `CLAUDE.md`.
2. Работай строго по этапам из раздела 11. Один этап — одна ветка, один PR. Перед этапом входи в plan mode и покажи план, затем реализуй.
3. Не начинай этап, пока не закрыты **блокирующие вопросы** этого этапа (раздел 1).
4. Любое отклонение от архитектуры (раздел 3) оформляй новым ADR в `docs/adr/`.

### Содержимое для `CLAUDE.md`

```markdown
# OCEAN — правила проекта
Стек: TypeScript везде. pnpm + Turborepo. apps/web (Next.js App Router, Tailwind), apps/api (NestJS, REST + OpenAPI),
packages/shared (zod-схемы, типы, деньги), packages/ui (дизайн-токены и компоненты). PostgreSQL 16, Redis, BullMQ, S3-совместимое хранилище.
Команды: `pnpm dev` (всё локально через docker compose), `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm db:migrate`, `pnpm db:seed`.

Жёсткие правила:
- Деньги только целыми числами в копейках (minor units). Никаких float. Валюта — RUB.
- Время хранить в UTC, показывать в часовом поясе организации.
- Интерфейс и тексты — русский по умолчанию, все строки через i18n-словарь, не хардкодить.
- Каждый запрос к данным организации фильтруется по org_id на уровне репозитория (не в контроллере).
- Переходы статусов заказа/лота/опциона — только через конечные автоматы в `apps/api/src/domain/*`. Прямой UPDATE статуса запрещён.
- Все денежные операции — только через леджер (двойная запись), идемпотентные ключи обязательны.
- Персональные данные не логировать. Секреты только из env, схема env валидируется zod при старте.
- Внешние сервисы (Госуслуги/ЕСИА, платежи, SMS, карты) — только за интерфейсами-адаптерами; в dev и тестах работают Mock-реализации.
- Дизайн: только токены из packages/ui, цвета не хардкодить. Следуй docs/PLAN.md §10.
- Definition of done: типы, тесты (юнит + интеграционные для автоматов и денег), миграция, обновлённый OpenAPI, a11y-проверка экрана, запись в CHANGELOG.
```

## 1. Допущения и открытые вопросы

### 1.1 Как я прочитал концепт (подтвердить)

| № | Допущение | Влияние |
|---|-----------|---------|
| A1 | **MVP (релиз R1)** = биржа + цифровое меню на вебе/PWA, логистику в R1 ведёт ops-команда через админ-панель вручную. **Бизнес-релиз (R2)** = автоматизированная доставка (хабы, маршруты, курьерское приложение, динамический тариф). В концепте написано «MVP — приложение/веб; БИЗНЕС — приложение/веб + доставка», я трактую это так. | Порядок этапов |
| A2 | Нативные приложения не делаем: **PWA** для всех ролей, включая курьера. React Native/Expo — после R2. | Сроки, стоимость |
| A3 | Комиссия 15% **удерживается из выплаты фермеру** (в концепте не сказано, кто её платит). Реализуем как настройку `commission_payer`. | Леджер |
| A4 | «Электронная подпись о качестве» в MVP = простая электронная подпись (подтверждение SMS-кодом + запись в аудит-лог), не квалифицированная. | Юридически — вопрос Q3 |
| A5 | «Рыночная цена» для опциона = индекс цены категории, считаемый по сделкам и лотам в Стакане за N дней (медиана). Определение в концепте отсутствует. | Этап 8 |
| A6 | В концепте «NFS» — опечатка, имеется в виду **NFC**. Метки: NFC-тег с NDEF-ссылкой + QR-код, ведущие на один и тот же URL. | Этап 6 |
| A7 | Рейтинг-веса (раздел 8) — стартовые, мои, калибруются по данным пилота. | Этап 5 |

### 1.2 Несостыковки в концепте (решить до этапа 8)

- В примере у поставщика «Put позволяет выкупить у него 20 кг стейков» — это право **покупателя купить**, то есть по определению **Call**. Put (право продать) в концепте для заказчика нигде не используется. **Рекомендация:** в первой версии опционов оставить только Call, Put убрать.
- В разделе «Заказчик» Call описан как «зарезервировать право на покупку эксклюзива», но механика эксклюзивности (кто ещё не может купить этот объём) не описана. Нужно решение: опцион резервирует объём у фермера (объём недоступен в Стакане) или нет.
- Логика исполнения «если рыночная цена > страйка» требует определения рыночной цены (A5).

| № | Вопрос | Блокирует | Моя уверенность / комментарий |
|---|--------|-----------|-------------------------------|
| Q1 | Интеграция с ЕСИА (Госуслуги) для юрлиц требует подключения к системе и, как правило, аккредитации/регистрации информационной системы. Срок и условия нужно проверить у оператора. | Этап 1 (боевой режим) | Уверенность средняя. В плане: адаптер + Mock + ручная верификация по ИНН (через открытые данные ФНС/выписку) как fallback. |
| Q2 | Эскроу («деньги не переводятся до приёмки, как на Авито») требует платёжного провайдера с отложенными расчётами/«безопасной сделкой» и расщеплением платежа (комиссия, логистика, выплата фермеру). | Этап 5 | Такие продукты есть у российских провайдеров (например, ЮKassa «Безопасная сделка», Т-Банк «Мультирасчёты»), но условия, лимиты и пригодность для B2B нужно проверить. Уверенность средняя. |
| Q3 | Юридическая рамка: договор-оферта платформы, признание ПЭП между участниками, статус OCEAN как оператора логистики. | Этап 4–5 | Нужен юрист. |
| Q4 | Опционы: в ГК РФ есть конструкции опциона на заключение договора и опционного договора (ст. 429.2, 429.3, уверенность высокая в том, что они существуют, номера статей проверьте). Но если продукт начнёт выглядеть как биржевой производный инструмент, возможны требования регулирования. Опционы нужно оформлять как **гражданско-правовой договор с физической поставкой товара**, без расчёта разницей. | Этап 8 | Нужен юрист до начала этапа. |
| Q5 | Хранение персональных данных граждан РФ: по закону первичная запись и хранение должны быть на серверах в РФ. | Этап 0 (выбор хостинга) | Уверенность высокая. Выбери облако с дата-центрами в РФ. |
| Q6 | Исходный **вектор логотипа** (SVG). Есть только PNG-скриншот. Claude Code не должен перерисовывать знак самостоятельно. | Этап 0 | — |

## 2. Требования

### 2.1 Функциональные (из концепта)

**Роли:** ПОСТАВЩИК, ЗАКАЗЧИК (ресторан, юрлицо), ПОСЕТИТЕЛЬ (гость), плюс технические: КУРЬЕР, ОПЕРАТОР (ops), АДМИН.

- **Посетитель:** регистрация по почте/номеру; профиль открытый или закрытый (влияет, какие данные сохраняются в истории заказов у ресторана); лента ресторанов и ферм; сканирование NFC/QR → меню с паспортами блюд; отзыв на блюдо (влияет на рейтинг ресторана в выдаче).
- **Поставщик:** вход/привязка через Госуслуги; профиль с позициями (например, «стейки мраморной говядины» + сертификат, прививки, корм); управление открытостью данных; выставление **лота** в Стакан (позиция + новые фото + нюансы партии); уведомление о заказе → подтверждение готовности с электронной подписью → получение **OCEAN IDF** (паспорт заказа) → прикрепление к боксу (можно купить фирменные боксы) → окно забора курьером → звонок за час до приезда.
- **Заказчик:** вход через Госуслуги, автоподтягивание ИНН, ОГРН, реестра проверок, статуса налогоплательщика; настройка предпочтений (категории, объёмы, бюджет); работа со Стаканом; корзина с расчётом доставки (База/Экспресс); опционы (Call) — в поздней фазе; приёмка по QR паспорта заказа; протокол возврата при браке; конструктор цифрового меню, куда автоматически попадают купленные партии.
- **Платформа:** Стакан лотов; рейтинг (LOSS, заполненность профиля, регулярность, объём, отзывы, количество отзывов; для ресторана ещё отзывы посетителей); штрафы + LOSS за беспричинный отказ или срыв поставки; деньги не переводятся до приёмки; комиссия 15%; логистический маржинальный доход; OCEAN+ (подписка); платное продвижение лотов; хабы и консолидация заказов.
- **Явно не делаем:** блокчейн, доставку частным лицам.

### 2.2 Нефункциональные [допущение, подтвердить]

| Параметр | Цель для пилота |
|----------|-----------------|
| Доступность | 99,5% |
| Задержка API | p95 < 300 мс на чтение, < 800 мс на запись |
| Обновление Стакана | до 2 с через SSE |
| Одновременные пользователи | до 2 000 (пилот), закладываем рост ×10 без переписывания |
| Консистентность | Нельзя продать один лот двум покупателям; нельзя потерять или дважды провести платёж |
| Платформы | Мобильный браузер/PWA в приоритете для гостя и курьера; десктоп в приоритете для поставщика и заказчика |
| Язык / валюта | Русский / RUB (i18n закладываем сразу) |
| Безопасность | RBAC, изоляция данных организаций, аудит-лог, соответствие локализации ПДн |

### 2.3 Ограничения

Команда: один владелец продукта + Claude Code. Поэтому: модульный монолит, один язык, минимум инфраструктуры, максимум готовых провайдеров.

## 3. Архитектура

### 3.1 Высокоуровневая схема

```
                        ┌────────────────────────────────────────────┐
  Гость (PWA, QR/NFC) ──┤                                            │
  Поставщик (web)    ──┤   apps/web  (Next.js)                       │
  Заказчик (web)     ──┤   • публичные страницы паспорта (SSR/ISR)   │
  Курьер (PWA)       ──┤   • кабинеты, Стакан, меню-конструктор      │
  Оператор (admin)   ──┤                                            │
                        └───────────────┬────────────────────────────┘
                                        │ REST + OpenAPI, SSE
                        ┌───────────────▼────────────────────────────┐
                        │   apps/api  (NestJS, модульный монолит)     │
                        │  identity │ catalog │ orderbook │ orders    │
                        │  logistics│ payments│ ratings   │ menu      │
                        │  options  │ notifications │ admin │ audit   │
                        └───┬─────────┬───────────┬──────────┬───────┘
                            │         │           │          │
                     PostgreSQL     Redis      S3-хранилище  Адаптеры
                     (источник    (кэш, SSE,   (фото, PDF,   ЕСИА, платежи,
                      правды)     BullMQ)      сертификаты)  SMS/IVR, карты
                                        │
                              Воркер (BullMQ): таймеры заказов,
                              резервы, рейтинг, индекс цен, уведомления
```

### 3.2 Стек

| Слой | Выбор | Почему |
|------|-------|--------|
| Язык | TypeScript | Один язык, общие схемы валидации между фронтом и бэком |
| Монорепо | pnpm + Turborepo | Просто, быстро, подходит для работы агента |
| Web | Next.js (App Router), React, Tailwind | SSR для публичных паспортов блюд (SEO, быстрый QR-переход), PWA |
| API | NestJS, REST + OpenAPI | Модули = границы будущих сервисов; OpenAPI → генерация клиента |
| БД | PostgreSQL 16 | Транзакции и блокировки нужны для Стакана и денег; JSONB для атрибутов позиций |
| ORM | Prisma (миграции) + сырой SQL для критичных блокировок | Скорость разработки без потери контроля |
| Очереди/кэш | Redis + BullMQ | Таймеры, ретраи, SSE-рассылка |
| Файлы | S3-совместимое хранилище в РФ | Подписанные URL, антивирусная проверка загрузок |
| Realtime | SSE | Односторонние обновления Стакана проще WebSocket |
| Тесты | Vitest, Playwright, Testcontainers | Интеграционные тесты на реальном Postgres |
| CI/CD | GitHub Actions, Docker | Сборка, тесты, миграции |

### 3.3 Структура репозитория

```
ocean/
├─ apps/
│  ├─ web/            # Next.js
│  └─ api/            # NestJS
│     └─ src/
│        ├─ modules/  # identity, catalog, orderbook, orders, logistics, payments, ratings, menu, options, notifications, admin
│        ├─ domain/   # конечные автоматы, чистая бизнес-логика без I/O
│        ├─ adapters/ # esia, payments, sms, ivr, routing, storage (+ mock-реализации)
│        └─ jobs/     # воркеры BullMQ
├─ packages/
│  ├─ shared/         # zod-схемы, типы, money.ts, enums
│  └─ ui/             # токены, компоненты, иконки, логотип

├─ infra/             # docker-compose, Dockerfile, deploy

```

### 3.4 Решения (ADR, кратко)

Полные ADR создать в `docs/adr/` по шаблону: Контекст → Решение → Рассмотренные варианты → Компромиссы → Последствия.

| ADR | Решение | Отвергнуто | Главный компромисс | Когда пересмотреть |
|-----|---------|------------|--------------------|--------------------|
| 001 | Модульный монолит | Микросервисы | Меньше гибкости масштабирования, зато в разы меньше операционной сложности | Когда один модуль (логистика/платежи) требует независимого масштаба или команды |
| 002 | PWA для всех ролей | Нативные приложения | Нет глубокой интеграции с ОС (фоновые push на iOS ограничены), зато одна кодовая база и мгновенный QR/NFC-вход без установки | Если курьерам нужна офлайн-работа и фоновая геолокация |
| 003 | PostgreSQL как единый источник правды, без блокчейна | Блокчейн для паспортов | Нет криптографической неизменяемости; компенсируем аудит-логом и хеш-цепочкой записей паспорта | Если партнёры потребуют внешней верифицируемости |
| 004 | Эскроу через платёжного провайдера + собственный леджер | Собственные номинальные счета | Зависимость от провайдера, зато нет лицензионных рисков | После выбора провайдера (Q2) |
| 005 | ЕСИА за адаптером, ручная верификация как fallback | Только ЕСИА | Ручная работа оператора на старте | Когда подключение ЕСИА будет получено |
| 006 | SSE для Стакана | WebSocket | Нет двусторонности, она здесь не нужна | При появлении чатов или встречных ставок |
| 007 | Опцион = договор с физической поставкой, только Call | Расчёт разницей, Put | Меньше гибкости, ниже регуляторный риск | После юридического заключения (Q4) |
| 008 | Резерв лота через условный UPDATE + TTL | Распределённые блокировки | Только пока один Postgres-кластер | При шардировании |

## 4. Модель данных

Все таблицы: `id` (uuid v7), `created_at`, `updated_at`; денежные поля — `*_minor bigint`; статусы — enum + автомат.

| Таблица | Ключевые поля и смысл |
|---------|-----------------------|
| `users` | email, phone, role_flags, visibility (`open`/`closed`) для гостя |
| `organizations` | type (`SUPPLIER`/`BUYER`), inn, ogrn, legal_name, tz, verification_status, esia_snapshot (jsonb), rating_score |
| `org_members` | user_id, org_id, role (owner/manager/staff) |
| `verifications` | org_id, method (`ESIA`/`MANUAL`), status, reviewer_id, payload |
| `categories` | дерево категорий (мясо, овощи, молочка…) |
| `attribute_templates` | category_id, поля позиции (сертификат, прививки, корм…), тип поля, обязательность |
| `positions` | supplier_org_id, category_id, title, attributes (jsonb), attribute_visibility (jsonb: что открыто гостям/заказчикам) |
| `position_documents` | position_id, kind, file_key, valid_until |
| `lots` | position_id, qty, unit, price_minor, ready_from, ready_to, best_before, lot_notes, status, version, reserved_until |
| `lot_photos` | lot_id, file_key, sort |
| `carts`, `cart_items` | buyer_org_id, lot_id, delivery_type |
| `orders` | buyer_org_id, supplier_org_id, status, delivery_type, goods_total_minor, delivery_total_minor, commission_minor, idempotency_key |
| `order_items` | order_id, lot_id, qty, price_minor |
| `order_idf` | order_id, token (подписанный), pdf_key, issued_at |
| `signatures` | order_id, signer_user_id, kind (`QUALITY_READY`), otp_ref, ip, signed_at |
| `hubs` | name, address, geo, working_hours |
| `shipments` | order_id, hub_id, courier_id, tariff_snapshot (jsonb), planned_pickup_at, picked_up_at, delivered_at |
| `routes`, `route_stops` | сборка развоза от хаба (R2) |
| `couriers` | user_id, status |
| `batches` | buyer_org_id, order_item_id, qty, received_at — **партия, полученная рестораном** (основа паспорта) |
| `menus`, `menu_items` | restaurant_org_id, dish, price, `menu_item_batches` (связь с партиями) |
| `tags` | restaurant_org_id, kind (`QR`/`NFC`), short_code, target (стол/блюдо/меню) |
| `reviews` | author_kind, target_kind (`DISH`/`SUPPLIER`/`BUYER`), target_id, score, text, verified_visit |
| `loss_events` | org_id, order_id, reason, fine_minor, created_at |
| `rating_snapshots` | org_id, score, components (jsonb), computed_at |
| `ledger_accounts`, `ledger_entries` | двойная запись, idempotency_key, order_id |
| `payments` | order_id, provider, provider_ref, status (`HELD`/`CAPTURED`/`REFUNDED`) |
| `options` | supplier_position_id, buyer_org_id, kind=`CALL`, qty, strike_minor, premium_minor, expires_at, status |
| `price_index` | category_id, day, median_minor, sample_size |
| `notifications` | user_id, channel, template, payload, status |
| `audit_log` | actor, action, entity, before/after, ip |

Индексы, обязательные с первого дня: `lots(status, category, ready_from)`, `orders(buyer_org_id, status)`, `orders(supplier_org_id, status)`, `ledger_entries(order_id)`, уникальные индексы по `idempotency_key`.

## 5. Заказ: конечный автомат и деньги

### 5.1 Статусы заказа

```
CREATED ──(оплата удержана)──► PAID_HELD ──(поставщик подтвердил, ПЭП)──► CONFIRMED
   │                              │                                          │
   └─(TTL резерва)─► EXPIRED      └─(поставщик отказал/не ответил)─► SUPPLIER_DEFAULT [LOSS + штраф, возврат]
                                                                              │
CONFIRMED ─► IDF_ISSUED ─► PICKUP_SCHEDULED ─► PICKED_UP ─► AT_HUB ─► OUT_FOR_DELIVERY ─► DELIVERED
                                                                                              │
                           ┌──────────────────────────────────────────────────────────────────┤
                           ▼                          ▼                                       ▼
                       ACCEPTED ─► PAYOUT_RELEASED   BUYER_REJECTED [LOSS + штраф]     CLAIM_OPENED ─► REFUNDED (без влияния на рейтинг)
```

Экспресс-заказ пропускает `AT_HUB` по прямому маршруту [допущение].

### 5.2 Правила

- Резерв лота при создании заказа: `UPDATE lots SET status='RESERVED', reserved_until=now()+interval '15 min', version=version+1 WHERE id=$1 AND status='LISTED'`. Если затронуто 0 строк, лот уже занят.
- Деньги: при `PAID_HELD` средства **удерживаются** у провайдера; выплата фермеру только после `ACCEPTED` (принцип «как на Авито»).
- Беспричинный отказ заказчика от приёмки → штраф + LOSS заказчику. Срыв поставки поставщиком → штраф + LOSS поставщику. Размеры штрафов в концепте не заданы: хранить в таблице настроек `penalty_rules`, значения утвердить владельцем.
- Брак при приёмке: открывается `CLAIM`, возврат средств, **рейтинг не страдает** (в концепте ответственность за транспортировку несёт OCEAN). Размер компенсации и порядок разбора с фермером/курьером нужно определить отдельно.
- Таймеры: подтверждение готовности поставщиком (SLA — задать), окно забора, звонок за 1 час до курьера, таймаут приёмки.

### 5.3 Леджер (двойная запись)

Счета: `buyer_funds_held`, `escrow`, `supplier_payable`, `ocean_commission`, `ocean_logistics_revenue`, `ocean_logistics_cost`, `fines`, `refunds`.
Проводки при `ACCEPTED`: escrow → supplier_payable (за вычетом 15%), escrow → ocean_commission, escrow → ocean_logistics_revenue. Любая проводка идемпотентна по ключу. Сумма по всем счетам в каждой транзакции равна нулю, это проверяется тестом и ночной сверкой.

### 5.4 Тариф доставки

`delivery = (base + per_kg·вес + per_m3·объём + per_km·расстояние) · коэффициент_тарифа · коэффициент_температурного_режима`
Коэффициенты хранятся в таблице `tariffs`, в заказе сохраняется `tariff_snapshot`. Маржа логистики = тариф в корзине − фактическая стоимость перевозки.

## 7. Опционы (этап 8, после юридического заключения)

- Только **Call** на физическую поставку: покупатель платит **премию** (удерживается в эскроу и уходит поставщику сразу; возврату не подлежит), фиксируется `strike`, `qty`, `expires_at`.
- До экспирации система присылает уведомление. «Исполнить» создаёт заказ по цене страйка из ресурса, зарезервированного поставщиком. Если не исполнить, опцион истекает, потеря = премия.
- Индикатор «в деньгах»: `price_index.median > strike` (A5).
- Поставщик не поставил по исполненному опциону → премия возвращается, штраф + LOSS.
- Вопрос эксклюзивности объёма (раздел 1.2) решить до разработки.

## 8. Рейтинг (стартовая формула, калибруется)

`score = 100 · Σ(wᵢ · fᵢ)`, где факторы нормированы в [0..1]:

| Фактор | Поставщик | Заказчик (ресторан) |
|--------|-----------|---------------------|
| Отсутствие LOSS (с затуханием за 12 мес.) | 0,30 | 0,25 |
| Заполненность профиля | 0,15 | 0,10 |
| Регулярность поставок/закупок | 0,15 | 0,15 |
| Объём | 0,10 | 0,10 |
| Оценки контрагентов (байесовское среднее, чтобы 1 отзыв не решал всё) | 0,20 | 0,15 |
| Число отзывов (уверенность) | 0,10 | 0,05 |
| Отзывы посетителей о блюдах | — | 0,20 |

Правила: пересчёт ночью + по событию (LOSS, приёмка); разложение по факторам видно владельцу рейтинга (прозрачность); новые организации стартуют с нейтрального значения, а не с нуля.

## 9. Безопасность, наблюдаемость, качество

- **Доступ:** RBAC + изоляция по `org_id` на уровне репозитория; тесты «организация A не видит данные организации B» обязательны для каждого модуля.
- **Гости:** публичный паспорт показывает только поля с флагом «открыто»; закрытый профиль гостя не попадает в историю заказов ресторана.
- **Файлы:** подписанные URL, проверка типа и размера, антивирус; сертификаты и документы по умолчанию приватные.
- **Защита:** лимиты запросов, защита OTP от перебора, CSRF, строгие cookie, заголовки безопасности, зависимость-аудит в CI.
- **Аудит:** любое изменение статусов, денег, верификаций и настроек пишется в `audit_log`.
- **Наблюдаемость:** структурные логи, трейсинг запросов, метрики (очередь, задержка SSE, число резервов/истечений, расхождения леджера), алерты на расхождение сверки.
- **Тесты:** юнит на автоматы и формулы; интеграционные на Postgres (гонка за лот: 50 параллельных покупок → ровно одна успешная; идемпотентность платежей; сумма леджера = 0); e2e Playwright на сквозной сценарий «лот → заказ → доставка → приёмка → выплата → блюдо в меню → паспорт».
- **Резервные копии:** ежедневные + восстановление проверять по расписанию.

- **Штамп-печать** (`<Seal/>`): круг со знаком «дерево над волнами», перемычки как у трафарета. Используется на паспорте блюда, на IDF, в успешной верификации организации. Размеры: 24 / 40 / 96 px. - **Возвышение:** без серых теней на карточках. Уровни — границы `--border` и тоновая подложка. Тень только у оверлеев (меню, модалки), синяя `--shadow-overlay`.

### 10.6 Движение

Не вызванное пользователем движение — ровно два места: (1) **«оттиск» печати** при открытии паспорта (масштаб 1.08→1, прозрачность, 240 мс, один раз); (2) **подсветка строки Стакана** при realtime-обновлении (фон `ocean-100` затухает за 600 мс). Остальное — только ответ на действие (раскрытие, подтверждение). Никаких каскадных появлений секций и hover-анимаций на каждой карточке. Уважать `prefers-reduced-motion`: оттиск и подсветка заменяются мгновенным состоянием.

### 10.9 Тексты

Голос: простой, активный, предложения с заглавной буквы, без восклицаний. Слово = одно действие.
- Кнопки: «Выставить в Стакан», «Подтвердить готовность», «Принять заказ», «Открыть претензию». Одно действие называется одинаково по всему потоку (кнопка «Выставить» → уведомление «Лот выставлен»).
- Термины предметной области оставляем как в концепте: **Стакан, Лот, Позиция, Паспорт заказа (OCEAN IDF), LOSS**. При первом появлении давать краткую подсказку («LOSS — отметка о срыве сделки, снижает рейтинг»), потому что рестораны не обязаны знать биржевой словарь.
- Ошибки объясняют, что случилось и что делать, без извинений: «Лот уже зарезервирован другим заказчиком. Выберите другой лот или подождите 15 минут: резерв может освободиться».
- Пустые состояния дают действие: «Лотов пока нет. Выберите позицию и выставьте первый лот».
- Слоган «от фермы до гостя без лишних волн» — только на брендовых экранах (вход, паспорт, письма), не на рабочих.

### 10.10 Доступность и адаптивность

WCAG 2.1 AA как минимум: видимый фокус (2px `ocean-600` с отступом), клавиатурная навигация по Стакану, `aria-live` для обновлений Стакана (вежливый режим), тач-цели от 44 px, семантическая разметка таблиц, alt-тексты фото лотов. Брейкпоинты: 360 / 640 / 1024 / 1280. Гость и курьер проектируются mobile-first, поставщик и заказчик — desktop-first с рабочей мобильной версией.

### 10.11 Проверка на шаблонность (результат ревью дизайн-плана)

Отвергнуто как «дефолт генерации»: кремовый фон с терракотой; чёрный фон с кислотным акцентом; газетная вёрстка с волосяными линиями; одинаковые скруглённые карточки с серой тенью и градиентами; капсовые надзаголовки и «→» в кнопках. Палитра задана брендом, поэтому оригинальность держится на трёх решениях: штамп-печать как центральный элемент, трафаретный язык перемычек, строгая табличная плотность Стакана.

## 11. План по этапам

Размер: S ≈ несколько дней, M ≈ 1–2 недели, L ≈ 2–4 недели работы одного человека с Claude Code (оценки ориентировочные, уверенность низкая, пересмотреть после этапа 1). Сроки и дедлайны не заданы концептом, их задаёт владелец продукта.

```
0 Основа ─► 1 Identity ─► 2 Каталог и лоты ─► 3 Стакан и заказ ─► 4 Жизненный цикл и логистика ─► [R1 пилот]
                                                    │                         │
                                                    └──────► 6 Гость и меню ──┤
                                               5 Деньги, штрафы, рейтинг ◄────┘
                                               7 Монетизация ─► [R2] ─► 8 Опционы ─► 9 Усиление
```

**Релизы:** R1 (пилот) = этапы 0–4 + минимум этапа 6, оплата через провайдера в тестовом режиме или ручная сверка, логистика вручную из админки. R2 = этапы 5, 7 + автоматизация доставки. R3 = этап 8.

### Этап 0 — Основа (S)

**Задачи:** монорепо; линтеры, форматирование, `typecheck`; docker-compose (Postgres, Redis, MinIO, почтовая заглушка); валидация env через zod; GitHub Actions; `packages/shared` (деньги, enums); `packages/ui` с токенами из §10.3, подключением шрифтов, страницей-каталогом токенов; логотип из векторного файла; сид-данные; `CLAUDE.md` и `docs/adr/001–008`.
**Приёмка:** `pnpm dev` поднимает всё одной командой; CI зелёный; страница токенов в светлой и тёмной теме; контраст пар «текст/фон» проверен автотестом.

**Промпт для Claude Code:**
> Прочитай `docs/PLAN.md` разделы 0, 3, 10. Создай монорепо по разделу 3.3, настрой инструменты и CI, реализуй `packages/ui` с токенами из 10.3 и страницей-каталогом. Не реализуй бизнес-логику. Покажи план до начала работ.

### Этап 1 — Идентичность, организации, верификация (M)

**Задачи:** вход по OTP (email/телефон); экран выбора ПОСТАВЩИК / ЗАКАЗЧИК / ПОСЕТИТЕЛЬ; организации и участники; `EsiaAdapter` + `MockEsiaAdapter` (отдаёт ИНН, ОГРН, реестр проверок, статус налогоплательщика); ручная верификация и очередь в админке; настройка открытости профиля гостя; предпочтения заказчика; аудит-лог; RBAC и изоляция по `org_id`.
**Приёмка:** тест «организация A не видит данные B»; верификация проходит и через Mock, и вручную; аудит-запись на каждое изменение статуса верификации.

> Реализуй этап 1 по `docs/PLAN.md` §4, §9, §11. ЕСИА — только через интерфейс-адаптер и Mock. Начни с интеграционных тестов изоляции организаций.

### Этап 2 — Каталог поставщика и лоты (M)

**Задачи:** категории и `attribute_templates` (по умолчанию для мяса: сертификат, прививки, корм); позиции с динамическими атрибутами и документами; флаги открытости каждого атрибута; форма лота с предпросмотром; загрузка фото и сертификатов (подписанные URL); автомат лота `DRAFT → LISTED → RESERVED → SOLD / WITHDRAWN / EXPIRED`.
**Приёмка:** лот нельзя опубликовать без обязательных атрибутов шаблона; закрытые атрибуты не отдаются публичным API (тест).

### Этап 3 — Стакан и оформление заказа (L)

**Задачи:** список лотов с фильтрами и поиском, SSE-обновления; корзина; расчёт доставки База/Экспресс по §5.4; резерв лота с TTL; создание заказа с идемпотентностью; интерфейс `PaymentProvider` с Mock (hold/capture/refund); уведомление поставщику.
**Приёмка:** нагрузочный тест: 50 параллельных покупок одного лота → ровно один заказ; обновление Стакана у второго клиента ≤ 2 с; повтор запроса с тем же `Idempotency-Key` не создаёт второй заказ.

> Реализуй этап 3. Начни с теста гонки за лот и условного UPDATE из §5.2, затем сервис заказа, затем UI Стакана по раскладке из §10.7.

### Этап 4 — Жизненный цикл заказа и логистика (L)

**Задачи:** конечный автомат §5.1; подтверждение готовности поставщиком с ПЭП (OTP) и записью в `signatures`; генерация OCEAN IDF (PDF с QR, подписанный токен); окно забора и уведомление о времени; задача для оператора «позвонить за час до забора»; админ-консоль: хабы, назначение курьеров, ручная консолидация; курьерское PWA (скан IDF при заборе, приём на хаб, выдача); приёмка заказчиком по QR; таймеры BullMQ.
**Приёмка:** сквозной e2e «лот → заказ → подтверждение → IDF → забор → хаб → доставка → приёмка»; неверный/чужой QR отклоняется; все таймеры переживают рестарт воркера.

### Этап 5 — Деньги, штрафы, LOSS, рейтинг (L)

**Задачи:** леджер §5.3; боевой `PaymentProvider` (после Q2); выплата только после `ACCEPTED`; штрафы и LOSS по `penalty_rules`; претензии и возвраты без влияния на рейтинг; расчёт рейтинга §8 с разложением на факторы; ночная сверка леджера.
**Приёмка:** сумма проводок каждой транзакции = 0 (property-тест); повторный webhook провайдера не дублирует проводки; рейтинг объясним: интерфейс показывает вклад каждого фактора.

### Этап 6 — Гость и цифровое меню (M–L)

**Задачи:** автоматическое создание `batches` при приёмке; конструктор меню (блюдо ↔ партии); публичные страницы `/p/{code}` и паспорт блюда (SSR, быстрый отклик по QR/NFC); генерация листов QR и инструкция записи NFC-тегов (NDEF-URL); регистрация гостя, лента ресторанов и ферм; отзывы о блюдах с проверкой визита (скан метки) [допущение]; ручной ввод заказа рестораном для случая «заказ сделан в заведении мимо OCEAN»; влияние отзывов на рейтинг ресторана в выдаче.
**Приёмка:** паспорт открывается < 1,5 с на мобильной сети (измерение Lighthouse); закрытые поля не видны; оценка блюда без сканирования метки отклоняется.

### Этап 7 — Монетизация и продвижение (M)

**Задачи:** комиссия 15% в леджере с отчётом; OCEAN+ (приоритетная обработка, бесплатная база при объёме, аналитика) — пороги объёма и цену задаёт владелец; платное продвижение лотов (поднятие, выделение) с прозрачной маркировкой «продвигается»; аналитика для поставщика и заказчика.
**Приёмка:** продвигаемый лот всегда помечен; ранжирование документировано и тестируется.

### Этап 8 — Опционы (L), только после юридического заключения (Q4)

**Задачи:** по разделу 7: выпуск, покупка, уведомление об экспирации, исполнение, индекс цен `price_index`, штрафы за срыв.
**Приёмка:** физическая поставка без расчёта разницей; сценарии «исполнен», «истёк», «поставщик не поставил» покрыты тестами; премия учитывается в леджере.

### Этап 9 — Усиление (M)

Нагрузочное тестирование, пентест, проверка резервного копирования и восстановления, раннбуки инцидентов, аудит соответствия хранению ПДн, мониторинг и алерты, оптимизация запросов.

## 12. Что пересмотреть при росте

- Разделить `payments` и `logistics` в отдельные сервисы, когда им понадобится независимое масштабирование.
- Заменить ручную консолидацию на оптимизацию маршрутов (задача VRP; рассмотреть OR-Tools) и подключить сервис маршрутизации.
- Вынести realtime Стакана в отдельный шлюз при росте числа подключений.
- Нативное приложение курьера (офлайн, фоновая геолокация).
- Шардирование и репликация чтения при росте нагрузки на Стакан.
- Пересчёт весов рейтинга по реальным данным и защита от накруток отзывов.
