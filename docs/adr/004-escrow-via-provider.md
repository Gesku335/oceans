# ADR 004 — Эскроу через платёжного провайдера

## Контекст

OCEAN удерживает деньги покупателя до приёмки товара (принцип «как на Авито»). Нужен механизм
безопасной сделки с расщеплением платежа (комиссия, логистика, выплата поставщику).

## Решение

Эскроу через российского платёжного провайдера с «безопасной сделкой» (ЮKassa, Т-Банк и др.)
плюс собственный леджер (двойная запись) для внутреннего учёта.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Эскроу провайдера | Нет лицензирования, готовая инфраструктура | Зависимость от провайдера |
| Собственные номинальные счета | Полный контроль | Лицензирование, регулирование |
| Прямые переводы | Простота | Нет защиты покупателя |

## Компромиссы

- Зависимость от провайдера: если он изменит условия — нужна миграция.
- Проводим параллельный леджер для сверки и отчётности.

## Последствия

- Интерфейс `PaymentProvider` с методами hold/capture/refund.
- Mock-реализация для dev и тестов.
- Сумма проводок леджера = 0 (проверяется тестом и ночной сверкой).

## Когда пересматривать

После выбора конкретного провайдера (вопрос Q2).
