# ADR 001 — Модульный монолит

## Контекст

OCEAN — B2B фермерская биржа. Один владелец продукта + Claude Code. Нужна архитектура, которая
масштабируется от пилота до нескольких тысяч пользователей без переписывания, но при этом
остаётся простой для маленькой команды.

## Решение

Один NestJS-приложение (`apps/api`) с модульной внутренней структурой:
`src/modules/{identity,catalog,orderbook,orders,logistics,payments,ratings,menu,options,notifications,admin}`.
Каждый модуль содержит свой контроллер, сервис и репозиторий. Доменная логика (конечные автоматы,
формулы) вынесена в `src/domain/`.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Микросервисы | Независимое масштабирование, изоляция | Операционная сложность, сетевая задержка, сложность для 1 человека |
| Модульный монолит | Простота развёртывания, одна БД, транзакции | Меньше гибкости масштабирования |
| Монолит без модулей | Ещё проще | Быстрая деградация кодовой базы |

## Компромиссы

- Один Postgres-кластер = нет горизонтального масштабирования записи.
- Модули sharing одну БД = нужна дисциплина границ (нет прямых JOIN между модулями, только через репозитории).

## Последствия

- При росте модуль (логистика/платежи) можно выделить в отдельный сервис, изменив только репозиторий.
- Turborepo позволяет мигрировать отдельные пакеты в репозитории при необходимости.

## Когда пересматривать

Когда один модуль требует независимого масштабирования или команды.
